## 6. Engineering standards
- TypeScript `strict`; no `any` (use `unknown` + narrowing); no unused code; no `console.log` (use the logger).
- One module per domain; thin controllers, logic in services; DTOs with `class-validator` for **every** input; explicit response mappers Ã¢â‚¬â€ never leak `passwordHash`, token hashes, `accountNumberEnc` or internal fields.
- Money only with Prisma `Decimal`; never JS floats. All multi-step writes in `$transaction`; stock via guarded `updateMany` (design Ã‚Â§4.5).
- Ownership/authorization enforced inside queries (design Ã‚Â§3.5); IDOR-safe `404`s.
- Stable error codes via one exception filter and the envelope in design Ã‚Â§2.2.
- Every endpoint documented in Swagger. Every non-trivial business rule has a unit test; critical flows have e2e tests (design Ã‚Â§10).
- Small, readable functions; meaningful names; comments only for non-obvious "why".
- Keep `.env.example` complete and README current.

### Decisions & deviations
- **COD risk (O2a, 2026-10-20):** phones are unverified, so the profile/cap is an explicit deterrent, not proof. `PhoneRiskProfile.phoneNormalized` is the canonical `+88Ã¢â‚¬Â¦` form (legacy raw numbers should be normalized before matching). The failure window is approximated from `lastEventAt` + `codRisk.windowDays`: a new failure after the window restarts the count at 1. Auto status only upgrades (OKÃ¢â€ â€™WATCHÃ¢â€ â€™BLOCKED); an admin-set RESTRICTED survives until the BLOCKED threshold, and whitelisted phones always assess OK. The address fingerprint is a secondary signal (same fingerprint contributes its status) and is never exposed to sellers.
- **COD caps (O2a):** only RESTRICTED phones are capped (`codRisk.restrictCap`, default Ã Â§Â³2000); WATCH is informational. Checkout computes totals first, then risk, then writes nothing on rejection. The error carries `{status}` / `{status, limit, grandTotal}` details and i18n copy points the customer to support (no online payment exists yet).
- **City/area scopes (O2a):** `CityScope.NA` is the backfill and the only value allowed for non-metro districts; `metroDistricts` is a setting (default `["Dhaka"]`). A seller can define CITY, OUTSIDE and ALL links for the same district (they are distinct scopes); duplicates for the same district+scope are rejected. The resolver is the single precedence implementation; cart has no city choice so it passes NA and only matches ALL/nationwide.
- **Replacements (O1b, 2026-10-19):** a replacement gets its own zero-total `Order` + one `ShopOrder(kind=REPLACEMENT, parentShopOrderId=Ã¢â‚¬Â¦)`; items are copied with zero price/commission, stock is decremented via the guarded update + `InventoryLog`, no `Payment` row is created, and the order starts in `PENDING` on the same state machine. `parentShopOrderId` is unique (at most one replacement per parent) and creation is idempotent (`createReplacementFromComplaint` returns the existing one on retry/conflict). Delivering a replacement skips `soldCount`, the seller ledger and payment recomputation; seller/admin analytics filter `kind=ORDER`, and the replacement `Order` is excluded by `shopOrders.some(kind=ORDER)`.
- **NOT_DELIVERED on DELIVERED (O1b):** allowed inside `complaint.windowHours` (48) like other delivered complaints; it increments `SellerProfile.falseDeliveryFlags` and sends an immediate `FALSE_DELIVERY_FLAG` notification to admins (the seller still gets the normal complaint notice). Phones are **unverified**, so the counter and COD risk are deterrents, not proof of fraud.
- **Complaint refund reversal (O1b):** resolving `RESOLVED_REFUND` always creates a `Refund(REQUESTED)` (amount = `refundAmount` or the shop order total) and immediately writes the `REFUND_REVERSAL` ledger entry. `LedgerEntry.refundId` makes it exactly-once; `RefundsService.process` reuses `LedgerService.reverseRefund` and skips if the reversal already exists. The refund is still paid out through the normal admin process flow.
- **Stuck-order cron (O1b):** one hourly transaction takes `pg_try_advisory_xact_lock(hashtext('planthaat:stuck-orders'))`; if another instance holds it the sweep exits silently. Reminders are time-gated (`stuck.reminderHours`, default 24) and capped (`stuck.maxReminders`, default 3), then `stuckFlaggedAt` is set and admins are notified. The customer delay notice is guarded by `ShopOrder.delayNotifiedAt` (one per shop order, sent as soon as `estimatedDeliveryTo` passes for CONFIRMED/PACKED/SHIPPED/FAILED_DELIVERY). Notifications are created in the transaction; emails are queued after commit.
- **Suspension bulk-cancel (O1b):** admin may cancel SHIPPED orders (state-machine exception for ADMIN), restock is on by default, COD pending payments are cancelled by the transition, and any `PAID` (future online) payment gets a `Refund(REQUESTED)` if none exists. Each cancellation emits the normal order-status event (customer notification); the seller is notified through the existing cancellation flow. One audit entry records the requested/cancelled/skipped counts.
- **Price changes (O1b):** `CartItem.priceSnapshot` is set when a line is added/updated (and backfilled). `GET /cart` compares it with the live variant price and returns per-line `priceChanged/from/to`, a shop flag and root `priceChanged/changedLineCount`. Checkout compares `expectedGrandTotal` with the freshly computed cart total **before** any idempotency/order write; a mismatch is `409 PRICE_CHANGED` with `{expectedGrandTotal, subtotal, deliveryTotal, grandTotal, changedLines}` and applies nothing, so the same Idempotency-Key can be retried after confirmation.
- **Payout hold semantics (O1a, 2026-10-19):** a positive ledger entry is `pending` until its `availableAt` (delivery + `payout.holdHours`, default 48h; if the shop order is not delivered yet, the clock starts when the entry is recorded). An open complaint on the same shop order (`OPEN`, `SELLER_RESPONDED`, `UNDER_REVIEW`) keeps all of that order's positive entries pending regardless of time. Negative entries are immediate (`availableAt = null`). `available` = unlocked positives Ã¢Ë†â€™ all negatives and may be negative; `owedToPlatform = max(0, Ã¢Ë†â€™available)`; `net = pending + available`. Payouts may only draw from `available`.
- **Backfill policy (O1a):** the migration backfills already-recorded positive entries using `ShopOrder.deliveredAt + 48h` (fallback `createdAt + 48h`); it does not alter amounts, so reconciliation results are unaffected. Future hold-window changes only affect new entries (no retroactive rewrite).
- **Money rounding:** all monetary math goes through `src/common/utils/money.ts` (Decimal, `ROUND_HALF_UP`, 2 dp). Checkout snapshots commission per line and sums the rounded line commissions; order totals are the sum of rounded line totals plus the rounded delivery charge.
